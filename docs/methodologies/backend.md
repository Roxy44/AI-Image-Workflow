# Методология: бэкенд

Справочник. Открывается, когда `backend.mdc` не даёт ответа: проектируем слой,
абстракцию, интеграцию или схему данных.

Язык не важен: на [Refactoring.Guru](https://refactoring.guru/design-patterns/catalog)
те же паттерны показаны для PHP, TypeScript, Python, Go и др. — смысл один, синтаксис
разный. Русское оглавление с PHP-примерами:
[refactoringu.ru](https://refactoringu.ru/ru/design-patterns/php.html).

## Архитектурные подходы

| Подход                                       | Когда подходит                                | Чем платим                                     |
| -------------------------------------------- | --------------------------------------------- | ---------------------------------------------- |
| Слоистый (controller → service → repository) | Дефолт для большинства сервисов               | При росте сервисы превращаются в «god service» |
| Гексагональный / порты и адаптеры            | Много внешних интеграций, нужна подменяемость | Больше интерфейсов и связующего кода           |
| Clean Architecture                           | Долгоживущий домен со сложными правилами      | Много слоёв, дорого для CRUD                   |
| Вертикальные слайсы по фиче                  | Команда хочет автономности фич                | Дублирование между слайсами                    |
| Микросервисы                                 | Разные жизненные циклы и масштабирование      | Распределённые транзакции, эксплуатация        |

Правило: начинать со слоистого монолита с чёткими границами. Микросервисы — ответ на
организационную, а не техническую проблему.

## Правило зависимостей

Домен не знает ничего о транспорте и БД. В файлах бизнес-логики нет импортов фреймворка
(`Request`, `Response`), ORM-моделей и SQL. Наружу — интерфейсы (порты), реализации
(адаптеры) внедряются на границе.

Проверка: можно ли вызвать бизнес-правило из теста без HTTP-сервера и базы? Если нет —
границы сломаны.

## Паттерны проектирования — как пользоваться каталогом

Паттерн — решение **повторяющейся** задачи проектирования, а не чеклист «внедрить все 22».
У Refactoring.Guru есть и раздел критики: навязанные паттерны усложняют простой код.

Перед добавлением:

1. Какая боль есть сейчас (дубли, связность, растущий `switch`)?
2. Какой паттерн снимает её **минимальной** новой поверхностью?
3. Хватит ли обычной функции и интерфейса? Если да — остановиться.

См. также [`design-principles.md`](design-principles.md) (KISS / DRY / SOLID) — паттерны
инструменты под этими дефолтами, а не замена им.

### Порождающие

| Паттерн                           | Задача на бэкенде                                  | Когда не нужен           |
| --------------------------------- | -------------------------------------------------- | ------------------------ |
| Factory Method / Abstract Factory | Семейства провайдеров (оплата, почта, стораджи)    | Одна реализация навсегда |
| Builder                           | Отчёты, сложные агрегаты, опциональные части       | DTO из двух полей        |
| Prototype                         | Дорогие шаблоны/конфиги, клон на запрос            | Дешёвые value object     |
| Singleton                         | Почти никогда в коде приложения; lifetime через DI | Скрытый глобальный стейт |

### Структурные

| Паттерн           | Задача на бэкенде                           | Когда не нужен              |
| ----------------- | ------------------------------------------- | --------------------------- |
| Adapter           | Обернуть SDK вендора своим портом           | API ваш и вы его меняете    |
| Facade            | Простой вход в сложный подсистемный кусок   | Фасад сам стал god-объектом |
| Decorator / Proxy | Ретраи, кеш, логирование, auth вокруг порта | Правки лезут в ядро класса  |
| Bridge            | Две независимые оси вариаций                | Меняется только одна ось    |
| Composite         | Деревья (меню, вложенные права)             | Плоские списки              |
| Flyweight         | Много похожих неизменяемых объектов         | Обычное число сущностей     |

### Поведенческие

| Паттерн                 | Задача на бэкенде                               | Когда не нужен                       |
| ----------------------- | ----------------------------------------------- | ------------------------------------ |
| Strategy                | Политики цены, налогов, сортировки, проверок    | Один алгоритм навсегда               |
| Template Method         | Общий сценарий с несколькими заменяемыми шагами | Шаги совсем разные — композиция      |
| Chain of Responsibility | Middleware, цепочки валидации                   | Порядок неочевиден, побочки прячутся |
| Command                 | Очереди, аудит, undo, сообщение как намерение   | Обработчик в одну строку             |
| Observer / Mediator     | Доменные события; меньше связей сервис↔сервис   | Событие на каждое поле               |
| State                   | Жизненный цикл заказа / тикета / платежа        | Хватает пары boolean                 |
| Iterator                | Стриминг больших выборок, свои коллекции        | Обычного цикла языка достаточно      |
| Memento                 | Черновики, откат в рамках сессии                | «Случайный» event sourcing           |
| Visitor                 | Редко: стабильный граф, много новых операций    | Граф часто меняется                  |

### Про «репозиторий»

В бытовом бэкенде Repository — чаще **порт персистентности**, не всегда GoF-паттерн.
Если снаружи строят деревья фильтров и знают семантику SQL — абстракция течёт: либо
сузить API запросов, либо честно жить с более тонким data mapper.

## Антипаттерны

- God service / god controller: HTTP + правила + SQL в одном классе.
- Анемичный домен, вся логика в контроллерах «для скорости».
- Преждевременные микросервисы и распределённые транзакции.
- «SOLID ради SOLID»: интерфейс с одной реализацией без тестов и без замены.
- Ловить всё в `Exception` и отдавать 500 на доменный конфликт (нужен 4xx).
- Статические синглтоны вместо DI с понятным временем жизни.

## Проектирование API

- Ресурсы — существительные, действия — методы. Глаголы в URL — только для явных команд
  (`/orders/{id}/cancel`).
- Пагинация с самого начала для растущих списков; курсорная — при часто меняющихся данных.
- Фильтры и сортировка — whitelist полей, без подстановки в запрос.
- Версия контракта решается заранее (`/v1/` проще всего); ломать без версии нельзя.
- Единый формат ошибки: код, сообщение, детали полей, id запроса.

| Ситуация            | Код           |
| ------------------- | ------------- |
| Невалидный ввод     | 400 (или 422) |
| Не аутентифицирован | 401           |
| Нет прав            | 403           |
| Нет ресурса         | 404           |
| Конфликт / дубль    | 409           |
| Лимит               | 429           |
| Сбой сервера        | 500           |

## Идемпотентность и надёжность

- `GET` / `PUT` / `DELETE` идемпотентны; `POST` — нет → ключ идемпотентности для оплат и
  создания.
- Внешние вызовы: таймаут, ограниченные ретраи с backoff + jitter, circuit breaker.
- Ретрай без идемпотентности → дубли (типичные «двойные списания»).

## Данные

- Схема только миграциями; у каждой есть откат или план отката.
- Индексы под реальные запросы; каждый индекс замедляет запись.
- Транзакция = один бизнес-инвариант; не держать в ней внешние HTTP-вызовы.
- Soft delete — осознанно: протекает во все запросы и уникальные индексы.
- N+1 ловить на ревью при добавлении связей.

## Наблюдаемость

- Структурные логи + correlation id.
- В логах id и метаданные, не тела и не PII.
- Метрики: RPS, ошибки, p95/p99.
- Liveness и readiness раздельно.

## Безопасность

Authn = «кто», authz = «можно» на каждом доступе к объекту. Плюс: rate limit, лимит тела,
проверка типов файлов, нет секретов в логах/ответах, CORS whitelist, нет деталей
исключений в 5xx.

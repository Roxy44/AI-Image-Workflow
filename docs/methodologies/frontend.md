# Методология: фронтенд

Справочник. В контекст агента не попадает автоматически — открывается, когда правило
`frontend.mdc` не даёт ответа: проектируем новую фичу, слой или структуру папок.

## Выбор структуры проекта

| Подход                                      | Когда подходит                                      | Чем платим                                     |
| ------------------------------------------- | --------------------------------------------------- | ---------------------------------------------- |
| Плоская (`components/`, `pages/`, `utils/`) | Мелкий проект, 1–2 разработчика, до ~30 компонентов | На росте `components/` превращается в свалку   |
| Feature-based (`features/<feature>/…`)      | Средний продукт, несколько команд                   | Нужна дисциплина: что «общее», а что фичевое   |
| Feature-Sliced Design (слои + слайсы)       | Большой продукт, долгий срок жизни                  | Порог входа, много правил импорта              |
| Модули по домену (`modules/<domain>`)       | Монолит с чёткими доменами                          | Границы легко размываются без линтера импортов |

Правило выбора: **не усложняй заранее**. Переход от плоской к feature-based дешёвый,
обратный — дорогой. FSD берут, когда команд больше одной и есть кому следить за слоями.
Структура всё равно подчиняется KISS / DRY / SOLID — см.
[`design-principles.md`](design-principles.md).

## Границы модулей

- У фичи есть публичный вход (`index.ts`), внутренности снаружи не импортируются.
- Импорт «фича → фича» напрямую запрещён. Общее выносится в `shared` / `entities` или
  поднимается на уровень композиции (страницу).
- Общее — это то, что уже используется в двух местах **и** не знает про домен. Иначе это
  преждевременная абстракция.
- Циклы импортов запрещены (`import/no-cycle`) — это самый честный индикатор сломанных
  границ.

## Состояние

Порядок выбора, от дешёвого к дорогому:

1. Локальное состояние компонента.
2. Подъём состояния к ближайшему общему родителю.
3. Контекст — для «редко меняющегося и широко нужного» (тема, локаль, текущий юзер).
4. Внешний стор — когда состояние переживает размонтирование и нужно многим ветвям.
5. Серверный кеш (react-query / RTK Query / SWR) — для данных с бэкенда.

Частые ошибки: серверные данные в глобальном сторе руками; контекст с часто меняющимся
значением (перерисовывает всё поддерево); дублирование состояния вместо вычисления.

## Данные и загрузка

- Три состояния обязательны: загрузка, пусто, ошибка. Плюс «повторить» для ошибки.
- Скелетоны вместо спиннера там, где известна форма контента.
- Оптимистичное обновление — только с откатом при ошибке.
- Данные валидируются на границе (zod / io-ts / ручной type guard), а не «по типам».

## Композиция компонентов

- Больше трёх булевых пропов — признак, что нужно разделить компонент или перейти на
  композицию (`children`, слоты).
- Пропы-конфиги (`variant`, `size`) хороши для дизайн-системы, плохи для бизнес-логики.
- Контейнер получает данные, презентационный компонент их рисует. Смешивание мешает
  тестировать и переиспользовать.
- Хук — правильное место для логики, которую нужно переиспользовать без разметки.

## Производительность

Сначала измеряем (React DevTools Profiler, Lighthouse, `performance.mark`), потом
оптимизируем. Порядок по эффективности:

1. Убрать лишние перерисовки: стабильные ключи, вынос состояния вниз, разделение
   контекстов.
2. Мемоизация (`useMemo`, `memo`) — точечно, по данным профайлера.
3. Разделение бандла: ленивые роуты и тяжёлые виджеты.
4. Виртуализация длинных списков (более ~100 элементов).
5. Изображения: правильные размеры, формат, `loading="lazy"`.

## Доступность

Минимум, который проверяем всегда: навигация с клавиатуры, видимый фокус, доступные имена
у интерактивных элементов, контраст текста, корректные заголовки, `aria-live` для
динамических сообщений. Модальные окна: ловушка фокуса и закрытие по `Escape`.

# Методология: принципы проектирования

Справочник. Конституция **P-6…P-8** уже требует KISS, DRY и SOLID при каждом изменении
кода. Открывайте этот файл, когда trade-off неочевиден, при разборе структуры или когда
в `stack.mdc` поле **CSS naming** = `bem`.

Это инженерный дефолт — не повод переписывать рабочий код (**P-3**).

## KISS — Keep It Simple, Stupid

Предпочитайте самое простое решение, которое **корректно** закрывает заявленную задачу.

| Делать                                               | Не делать                                             |
| ---------------------------------------------------- | ----------------------------------------------------- |
| Прямой код, который коллега читает с первого прохода | Вкладывать фреймворки, DI-графы или конфиг «на потом» |
| Один понятный поток управления                       | «Умные» однострочники, скрывающие смысл               |
| Убирать мёртвые ветки, когда задача их касается      | Оставлять спекулятивные хуки и неиспользуемые флаги   |

Тест: если слой / интерфейс / опцию можно убрать и требование всё ещё выполняется —
уберите. Сложность нужна только с причиной в одном предложении.

## DRY — Don't Repeat Yourself

Не дублируйте **нетривиальное** знание (правила, формулы, таблицы маппинга). Дублировать
тривиальный glue или два коротких похожих JSX-блока нормально, пока форма не стабильна.

| Сигнал                                                   | Действие                                            |
| -------------------------------------------------------- | --------------------------------------------------- |
| Одна и та же логика в двух местах и оба должны совпадать | Вынести в общую функцию / модуль                    |
| Похожая форма один раз, второй раз может не случиться    | Оставить; выносить на втором реальном использовании |
| «Общий» хелпер с кучей флагов под разных вызывающих      | Плохая абстракция — разделить или инлайнить         |

Плохая абстракция дороже дублирования. Короткая копия с комментарием лучше «универсального»
хелпера, который никто не понимает.

## SOLID

Применяйте в масштабе задачи. Скрипту на 30 строк не нужны пять интерфейсов.

| Буква                     | На практике                                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S**ingle Responsibility | У модуля / типа / функции одна причина меняться. Резать god-единицы «fetch + render + format».                                                                            |
| **O**pen–Closed           | Расширять композицией / новыми типами, а не править каждый call site под каждый вариант — когда варианты реальные, не вымышленные.                                        |
| **L**iskov Substitution   | Подтип соблюдает контракт родителя. Без сюрприз-исключений и игнора параметров в overrides.                                                                               |
| **I**nterface Segregation | Узкие интерфейсы под нужды вызывающего. Не заставлять клиента зависеть от неиспользуемых методов.                                                                         |
| **D**ependency Inversion  | Высокоуровневая политика зависит от абстракций, уже принятых в проекте (порты, injected-клиенты), а не от конкретных HTTP/БД — на границах, важных для тестов или замены. |

Тест перед новым интерфейсом или слоем: даёт ли он вторую реальную реализацию, тест без
I/O или понятную границу команды? Если нет — побеждает KISS.

Паттерны из `docs/methodologies/backend.md` — инструменты под SOLID/KISS, а не чеклист
«внедрить все 22 классики».

## BEM (опционально)

Только если **CSS naming** в `project/stack.mdc` = `bem`. Иначе этот раздел не читать.

**Жёсткий skip:** если стек стилей — Tailwind / UnoCSS / CSS-in-JS, BEM неприменим. Не
выдумывать `block__element` рядом с utility-классами или `styled`-компонентами — такая
смесь баг. В таких проектах держат `CSS naming: n/a`.

BEM = Block / Element / Modifier для **имён классов** в классическом CSS, SCSS или CSS
Modules (локальные имена всё равно следуют соглашению).

| Часть    | Форма                                                      | Пример                                 |
| -------- | ---------------------------------------------------------- | -------------------------------------- |
| Block    | `block-name`                                               | `card`                                 |
| Element  | `block-name__element`                                      | `card__title`                          |
| Modifier | `block-name--modifier` или `block-name__element--modifier` | `card--featured`, `card__title--large` |

Правила:

- По возможности один block на корень компонента; элементы — под этим block.
- Modifier меняет состояние или вариант — не заводить новый block ради мелкой визуальной
  правки.
- Не смешивать BEM с ad-hoc глобальными классами в одной фиче.
- В гибриде (например Tailwind + несколько SCSS-блоков) BEM только для **классических**
  своих классов, никогда внутри строк utility-классов.

Если в репозитории уже есть диалект (`_` вместо `__`, camelCase-блоки) — совпадать с
**существующими** файлами: consistency важнее учебника (**P-2**).
